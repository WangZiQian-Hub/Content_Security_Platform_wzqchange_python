# 数据处理实现说明

实际运行目录是根目录 `back/` 与 `src/`；`back/app/main.py` 通过 `/api/v1` 挂载后端，Vite 前端代理到 8000。数据接入在 `task_service.py` 中先规范化字段，再调用 `create_dataset_version()`，最后把每行写入带 `dataset_version_id` 的 `dataset_records`。旧版本不更新，`datasets.version` 只指向当前版本。

## 设计决定

1. 重复口径沿用接入链路的 `normalize_content()`：正文转文本、去除全角空格、连续空白折叠、`casefold()`；标题不同但正文相同仍算重复。字段为空先按字段规则淘汰，不参与去重；字段缺失等同空值。
2. 同组保留源版本中 `dataset_records.id` 最小的行。源行固定按 ID 升序读取，因此重跑结果确定。
3. 只在用户选中的一个数据集版本内判重；跨版本判重会使输出依赖历史版本，且与版本快照语义冲突。
4. 固定顺序为“字段补全，再去重”。这样重复统计只针对可用样本，缺字段样本只记字段规则。
5. “存在”定义为 `text_value()` 后非空。接入链路已有同一规定；因此存量缺标题、缺正文或两者都缺的行会在勾选字段补全时被丢弃，不会改动源行。
6. 输出沿用接入版本机制：新增 `dataset_versions` 行，新增输出版本的 `dataset_records` 行，并切换当前版本；源版本和源行只读。输出版本记录数、任务 `retained_count/success_count` 均为保留行数。
7. 新增 `process_audits` 表，每条淘汰行记录源行 ID、规则、原因、保留行 ID和原 payload；接口为 `/data-governance/process-tasks/{task_id}/audit`。
8. 任务 `total_count` 是选中源行数，`processed_count` 是实际扫描数，`retained_count/success_count` 是新版本行数，`duplicate_count` 与 `anomaly_count` 分别是两条规则淘汰数；新版本 `stored_record_count` 与保留数一致。
9. 处理按版本一次性读取，适用于现有接入上限 100,000 行；JSON payload 不做跨版本扫描，也不修改源数据。任务 JSON 只保留前 200 条对比，完整输出仍在版本快照和审计表中。后续更大规模应改为分批游标，但不改变语义。
10. 预览只读库，不创建任务、版本或审计；返回真实源行的原文、处理后文本、保留/丢弃动作和规则字段。
11. 只执行两个已知规则。历史任务中的未知规则原样保留在 input，计入 `unknown_rule_count`，不伪称已执行；详情仍可回看。
12. `_evaluate()` 是纯函数，覆盖字段空值、正文归一化（大小写/全角空格/连续空白）、稳定保留和未知规则；真实接口验证另见验收记录。

## 数据库变更

只新增 `process_audits` 表及 `task_id/source_record_id` 索引；没有删除、改名、改类型或重写已有表/行。服务启动使用既有 `Base.metadata.create_all()`，缺表时创建，已存在表不变。

## 代码与测试

- `back/app/services/data_processing.py`：真实预览、规则执行、版本输出与审计事务。
- `back/app/models/tables.py`：新增 `ProcessAudit`。
- `back/app/routers/tasks.py`：处理任务后台执行、失败回滚和失败状态。
- `back/app/routers/data_governance.py`：只下发两条真实规则、真实预览、真实样本查询和审计查询。
- `back/tests/test_data_processing.py`：确定性去重、字段淘汰和未知规则测试。

前端未修改；已有数据处理 API、store 和页面测试保持通过。

## 回滚方案

停止后端后，按本次任务 ID 定向删除其 `dataset_records`、`process_audits`、输出 `dataset_versions` 和 `tasks` 行，并把 `datasets.version/is_current` 恢复到任务记录的源版本；禁止全表删除。代码回滚恢复上述四个文件，`process_audits` 表可保留（或仅在确认无引用后按表名删除）。
